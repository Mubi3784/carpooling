## Design decisions
1. Matching engine is pure and lives in `utils\matching.js`, takes plain objects plus `now`, never touches the DB and never mutates inputs. Thresholds are named exported constants. Rationale: easiest to unit test every rule row.
2. Matching is computed at read time, nothing is stored. Candidates are fetched by one indexed query (same date, ACTIVE, `expiresAt > now`, `availableSeats > 0`, not own), then ranked in memory. Cap 100 candidates per call.
3. Count form (cost control): `GET /api/requests/matches/counts` (owner-only, single batched call). Cost: 1 query for the caller's active future requests (already indexed on passenger) + 1 query for all candidate rides across the distinct dates (`rideDate: {$in: dates}`, `.select` of only matching fields, `.limit(300)`), then in-memory matching. 2 queries total regardless of request count (max 7 active items per user), no N+1. Counts count EXACT+CLOSE+ALTERNATIVE and also return `exact` count. Document this in a code comment. Route must be registered before `/:id`.
4. Existing-match flag: one `RideMatch.find({ passenger, ride: {$in: rideIds}, status: {$in: ['PENDING','ACCEPTED']} })` per call, returned as `existingMatch: 'PENDING' | 'ACCEPTED' | null` per ride (no ids of other users).
5. Time distance uses `departureDateTime` minute difference (absolute), so it is timezone-safe. Text matching uses normalised tokens.
6. Filter validation: every new query param must be `typeof === 'string'` (arrays/objects give 400), length limited (pickup/destination 50), regex-escaped, `minSeats` integer 1..6, times `HH:mm`. If both timeFrom and timeTo are given and timeFrom > timeTo: 400. For rides, time filtering uses the `departureTime` string (same as existing request filter, HH:mm lexicographic is correct).
