## Decisions and ambiguities

D1. Combined cap. Add `MAX_ACTIVE_FUTURE_ITEMS_PER_USER` in `rideLimits.js` as an alias: `const MAX_ACTIVE_FUTURE_ITEMS_PER_USER = MAX_ACTIVE_FUTURE_RIDES_PER_USER;` (keep the old export so P2 code and tests are unchanged; do not introduce a second number). New helper `backend/utils/activeItemCount.js` with `countActiveFutureItems(userId)` = active+FULL future Rides (driver) + ACTIVE/MATCHED future RideRequests (passenger), `expiresAt > now`. Both `createRide` (replace its own count with the helper) and `createRequest` use it. Documented in the plan file: a user who is both driver and passenger shares one budget of 7. Cap is best effort under concurrency (same as P2). MATCHED requests count (still upcoming); CANCELLED/expired do not.
D2. Failed accept (seat update returns null): leave the match PENDING and return 409 "No seats left or ride no longer available". Reason: seats may free up if another match is cancelled and the acceptor can still decline. Exception: if the ride is missing/expired/CANCELLED, mark the match CANCELLED (nothing to wait for) and return 409/404. Never write ACCEPTED before the seat update succeeds.
D3. Accept ordering and rollback: (1) atomically claim the match `PENDING -> ACCEPTED` via `findOneAndUpdate({_id, status:'PENDING', responder}, ...)`; (2) atomically decrement seats; if (2) fails, revert the match to PENDING (`findOneAndUpdate({_id, status:'ACCEPTED'})`) and return 409. Claiming the match first prevents double-accept of the same match from decrementing twice; the conditional ride update prevents overselling across different matches. No transactions (Atlas free replica set supports them, but the memory server is standalone; avoid them).
D4. Seat decrement for Ride: `Ride.findOneAndUpdate({_id, status:'ACTIVE', availableSeats:{$gte:n}, expiresAt:{$gt:now}}, [{ $set: { availableSeats: {$subtract:['$availableSeats',n]}, status: {$cond:[{$eq:[{$subtract:['$availableSeats',n]},0]},'FULL','$status']} } }], {new:true})` (pipeline update so FULL is set in the same atomic op). Restore on cancel: pipeline update `availableSeats = min(totalSeats, availableSeats+n)`, `status = FULL->ACTIVE if result > 0`, filter `{_id, status:{$in:['ACTIVE','FULL']}}`; if the ride is gone or expired, skip silently.
D5. Model name `RideMatch` (collection `ridematches`). Responder = the party that did not initiate; store `driver`, `passenger`, `initiatedBy`; responder computed from these.
D6. Passenger in `GET /api/requests` is shown as first word of `name` or "Passenger"; no ids of the passenger are required for drivers, so return no passenger id (prevents profile probing).
D7. Decline of Flow B "Request to Join" with a linked request: request stays ACTIVE. Cancel of PENDING: request stays ACTIVE.
D8. Unique partial index for RideMatch `{ride:1, passenger:1}` for status in PENDING/ACCEPTED, as the spec says. "Declined cannot be re-sent": in `createMatch`, before insert, check for any DECLINED match for (ride, passenger) -> 409 "This offer was declined". CANCELLED does not block re-sending (the initiator cancelled, user may retry); document.
D9. Idempotency for matches: `clientMatchId` (same pattern as SERIES_ID_PATTERN) stored on the doc with unique partial index `{initiator, clientMatchId}`; replay returns the existing match with 200. On a dup-key from the (ride, passenger) index for a different clientMatchId return 409 "already pending or accepted".
D10. Expired requests: `status` stays ACTIVE in DB; responses compute `status: 'EXPIRED'` when `expiresAt <= now` and status is ACTIVE/MATCHED... only ACTIVE is derived EXPIRED; a MATCHED request past expiry also shows EXPIRED (derived). Document it.
D11. Alerts count = PENDING matches where caller is the responder and `expiresAt > now` + matches the caller initiated whose status changed to ACCEPTED/DECLINED/CANCELLED-by-other and `initiatorSeenAt` is null (+ for responder, cancelled-by-initiator after accept is unseen). Implement with per-party seen flags: `seenByDriver`, `seenByPassenger` booleans. Set the OTHER party's flag false on every state change; the actor's flag true. Pending incoming = responder's flag false at creation. Count = matches where (me is driver and seenByDriver=false) or (me is passenger and seenByPassenger=false), not expired. `POST /:id/seen` sets my flag true. Because PENDING incoming counts until seen or acted on, acting also sets the actor's flag true.
D12. Rate limit: `createRateLimiter` for POST /api/requests (10 / 10 min) and POST /api/matches (30 / 10 min), and accept/decline (60 / 10 min), defined in the route files. Test env: the in-memory limiter keys per IP; set generous limits via constants and make the test suite not hit them (if a test exceeds, read how authRoutes handles it in tests and follow it; do not disable in prod).
